# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Bag3l is a scripting language implemented in Go. The `bag3l` CLI compiles and
runs `.b3` programs on a custom stack-based VM. The standard library lives
under `lib/` and is largely generated from `.stubgen` specs.

## Common commands

- Build the CLI: `go build ./cmd/bag3l`
- Run a script: `go run ./cmd/bag3l path/to/program.b3`
- Run an inline command: `go run ./cmd/bag3l -c "<bag3l code>"`
- CPU profile a run: `go run ./cmd/bag3l -p cpu.prof program.b3`
- All tests: `go test ./...`
- Tests for one package: `go test ./tests` or `go test ./lib`
- Single test: `go test ./tests -run TestForLoop`
- Regenerate parser/lexer and stub code: `go generate ./...`
  - Parser/lexer are generated from `internal/parser/parser.lox` and
    `lexer.lox` (loxlex toolchain — produces `*.gen.go`).
  - Each `lib/<pkg>` with a `<pkg>.stubgen` file is generated by the in-tree
    tool at `internal/stub/stubgen` via `//go:generate stubgen <pkg>.stubgen`.

## Architecture

The top-level package `github.com/dcaiafa/bag3l` (`nitro.go`) is a thin public
facade re-exporting types from `internal/vm`, `internal/compiler`, etc., so
embedders import a single package.

Pipeline from source to execution:

1. **Parse** (`internal/parser`): A loxlex-generated lexer/parser
   (`lexer.gen.go`, `parser.gen.go`) consumes `.b3` source and produces an AST
   in `internal/ast`. Grammar lives in `parser.lox` / `lexer.lox`; regenerate
   with `go generate`.
2. **Compile** (`internal/compiler`): Resolves imports via `internal/mod`
   (package resolver) and `internal/fs` (pluggable filesystem), runs scope
   analysis (`internal/scope`, `internal/symbol`), and emits bytecode using
   `internal/vm/emitter.go` into `vm.CompiledPackage` / `vm.Program`. Errors
   flow through `internal/errlogger`.
3. **Execute** (`internal/vm`): Stack-based VM (`vm.go`, `instr.go`) with
   first-class iterators (`iterator.go`), regex, maps (`Object`), lists
   (`Array`), and closures. Concurrency uses cooperative coroutines built on
   `internal/fiber`. Read/write streaming uses `Reader`/`Writer` abstractions
   backed by `internal/ioqueue` / `internal/bytequeue`. See `docs/vm.md` for
   the runtime architecture in depth: data structures, calling convention,
   instruction set, iterators, defer/try-catch, coroutines, and known quirks.
4. **Metadata** (`internal/meta`): `@info`, `@param`, `@flag` directives at the
   top of a script declare program-level metadata consumed by `cmd/bag3l` to
   build per-program flag/arg parsing (see `cmd/bag3l/flags.go`).

### Builtin library (`lib/`)

`lib/` is the bag3l standard library, exposed as importable bag3l packages
(`global`, `str`, `int`, `float`, `list`, `maps`, `bool`, `time`, `os`, `file`,
`io`, `path/filepath`, `crypto`, `encoding/csv`, `encoding/hex`, `regex`,
`runtime`, `core`, `testexec`, etc.).

Most packages are written with **stubgen**: each package has a `<pkg>.stubgen`
file declaring bag3l-visible function signatures, overloads, and type
conversions; running `go generate` produces `<pkg>.stubgen.go` with the
argument-parsing and dispatch boilerplate. See `internal/stub/README.md` for
the stubgen language reference.

`lib/global` is the package whose symbols are visible without an import. The
historical `lib/lib.go` `GlobalPackage` registry is being migrated function by
function into `lib/global` using stubgen (see `lib/SPEC.md` for the migration
plan and in-progress checklist; functions that can't be expressed in stubgen
are marked `// REVISIT`).

### Tests

- `tests/` holds end-to-end language tests — each `*_test.go` exercises a
  language feature (`for`, `if`, `try/catch`, pipelines, etc.) by compiling
  and running snippets, with helpers in `internal/btesting`.
- `lib/**/*_test.go` covers individual builtin functions; many use the
  `lib/testexec` helpers.

## Conventions

- After modifying any `*.lox` grammar or `*.stubgen` spec, run
  `go generate ./...` and commit the regenerated `*.gen.go` / `*.stubgen.go`
  files alongside the source.
- The migration of global builtins into `lib/global` (see `lib/SPEC.md`) uses
  one commit per converted function/file; preserve that convention when
  continuing the migration.
